# ADR-0004：会话交接产生的卫星文档，必须能从 STATUS.md 被发现（交接文档索引）

- **状态**：accepted
- **日期**：2026-08-01
- **补记**：否

## 背景 Context

下游真实使用项目 `hermes-nas-experiment` 在 2026-07-31 限流期间发生了一次
AI 会话交接（Claude chat 因额度限流，临时由 Claude Code 接管协调工作，
限流结束后交还）。交接产生了两份独立文档（`2026-07-31-限流期接续工作
总纲.md`、`2026-07-31-待Claude-chat拍板清单.md`），完整记录了交接时的
已知事实、未完成事项、活跃决策——**完全符合规则14的要求**，不是没记。

但这两份文档独立于 STATUS/CHANGELOG/ADR/SOP 四件套之外，STATUS.md 里
没有留下任何指向它们的痕迹。2026-08-01，一个全新的对话窗口打开该项目，
按标准流程读完 STATUS → CHANGELOG，完全不知道这两份文档存在，直到一个
不属于规范内角色的第三方审核者，在做无关的另一项审计任务时偶然扫到
文件名，才把这个缺口带出来。**这是运气，不是设计。**

核心问题：规则14 只规定了"交接时要记录什么"，没规定"如果交接记录是
独立于四件套之外的卫星文档，必须让后来者可以从 STATUS.md 单一入口
发现它"。"记录得详细"和"记录能被找到"是两件不同的事，前者解决完整性，
后者解决发现性，这次事故证明只做到前者是不够的。

## 考虑过的选项 Options Considered

1. **维持现状**：依赖规则14要求的交接记录内容详实，不额外要求索引
   - 优点：不增加新概念
   - 缺点：这次事故已经证明"记录详实"不等于"可被发现"——这是本质
     不同的两类失效模式，前者不能替代后者

2. **要求会话交接必须直接写进 CHANGELOG 本身，不允许产生独立卫星文档**
   - 优点：天然可发现（CHANGELOG 是四件套之一，是必读项）
   - 缺点：交接记录往往包含大量过程性内容（详细任务分工表、多轮讨论
     记录），硬塞进 CHANGELOG 的结构化字段会破坏"CHANGELOG 是简洁
     时间线"这个定位，表达力会打折扣

3. **在"毕业文件"清单里新增一类"交接文档索引"，要求任何产生独立卫星
   文档的交接，必须同步在 STATUS.md 建立一行可发现的索引（已选定）**
   - 优点：不强制改变交接文档本身的自由格式，只要求"存在性必须被
     索引"，改动成本低、破坏性最小，与 blackbox 一贯"不重复记两遍，
     只是不同视图"的设计风格一致（参照规则5 对已知盲点表与 CHANGELOG
     关系的处理方式）
   - 缺点：多一条要记的规则，需要 agent 养成新习惯

## 决定 Decision

采用方案 3。在 SKILL.md"毕业文件"一节新增"交接文档索引"类别：任何
AI 协作场景下的会话交接（命中规则14）如果产生了独立于 STATUS/
CHANGELOG/ADR/SOP 之外的卫星文档，必须同步在 STATUS.md 新增/更新
"历史交接文档索引"小节，格式为：文件名 + 一句话摘要 + 归档状态。
同步更新 `assets/STATUS_TEMPLATE.md`，加入这一节的占位示例。

## 理由 Rationale

- 这次事故的根源是"发现性"缺陷，不是"完整性"缺陷——记录本身写得
  很详细，但没人知道该去哪儿找。方案3直接对症下药，且成本最低
- 与 blackbox 整体的判断标准一致（"不知道背景但知道去哪儿找的人，
  能不能安全接手继续工作"）——这条规则补的正是"知道去哪儿找"这一半，
  此前只顾着确保"记录本身完整"，漏了"记录本身可被发现"这个前提

## 不确定性 Uncertainties

- 这条规则依赖 agent 自觉在交接完成后回头补 STATUS 索引，暂无技术
  强制手段——与 STATUS 软锁、共享规范同步推送是同一类局限（软约束，
  不是硬约束）
- 尚未在更多真实项目里验证这条规则本身是否够用。目前只要求"文件名+
  一句话摘要+归档状态"三个字段，是否需要更多字段（比如产生日期、
  涉及哪些具体决策编号）有待观察

## 撤销/回退方案 Rollback Plan

如果这条规则在实践中被证明是噪音（比如某类项目交接频率很高，索引
本身变得庞大难维护），可以收紧适用范围（比如只要求"交接产生了实质性
方向决策"的文档才需要索引，纯操作记录不需要）——退回方式是修改
SKILL.md 里这条规则的适用范围，不需要推翻整个"毕业文件索引"机制本身

## 接受的风险/未处理的问题 Accepted Risks

- 没有覆盖"交接文档索引本身也可能被遗漏"这种递归情况——如果 agent
  连"要建索引"这条规则本身都忘了执行，同类问题依然会重现。目前只能
  靠这条规则写得足够显眼（紧跟在毕业文件清单里、SKILL.md 会被作为
  操作规范通读）来降低遗漏概率，无法从机制上彻底杜绝

## 影响 Consequences

- 好处：任何使用 blackbox 的项目，只要发生 AI 会话交接并产生了卫星
  文档，未来任何一个全新会话都能通过 STATUS.md 这一个入口发现它，
  不再依赖"审核者恰好扫到文件名"这种运气
- 代价：STATUS.md 多一个需要在交接发生时维护的小节

## 发现来源

下游真实使用项目 `hermes-nas-experiment`，2026-08-01，由该项目的第三方
审核者（opencode）在执行另一项无关审计任务时偶然发现两份未被索引的
交接文档，经协调者（Claude chat）确认为通用方法论层面的缺口，非该
项目独有问题，追溯到 blackbox 本体修复。
