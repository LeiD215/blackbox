# ADR-0005：多 Agent 并行协作场景补丁（CHARTER/任务归属追踪表/协作协议/
证据类型字段/凭据处理/框架自检）

- **状态**：accepted
- **日期**：2026-08-13
- **补记**：否

## 背景 Context

下游真实使用项目 `hermes-nas-experiment` 在 2026-08-13 单日内，同时有
两个具名 Claude Code 执行体（代号"哨兵"负责基础设施、"驻站"负责主线
项目）并行工作，暴露出 blackbox 当前设计假设的场景（单个 agent 隔一段
时间回来，靠线性历史记录重建状态）无法覆盖"同一时刻多个具名 agent 需要
知道'这条归谁'"这类真实协作问题。当天同时暴露：任务归属撞车、协调者
↔执行 agent 间缺一层实时派发通道、任务编号跟仓库章节号打架、验证方法
共享系统性盲区、"形式正确但关键一层未生效"反复出现、间接推断代替直接
核实、真实凭据落笔未先脱敏、CHANGELOG 关键字段存在合法逃逸空间、
STATUS.md 单文件体量超过 200KB 违反自身"快照而非历史"定位——共 9 条
具体证据（完整证据链见下游项目 `docs/ai-review-drafts/2026-08-13-
blackbox补丁提案-多方AI咨询稿.md`）。

## 考虑过的选项 Options Considered

1. **维持现状，不改动 blackbox 本体**
   - 优点：保持框架极简（16 条规则，无判断空间）
   - 缺点：证据链已经证明这些不是偶发问题，多 agent 协作是 blackbox
     未覆盖的一整类真实场景，不动会持续在下游项目复现同类事故

2. **原样采纳下游项目提出的 7 条初稿提案**
   - 优点：响应速度快
   - 缺点：初稿本身存在结构问题——把不同性质的补丁（结构性新文件/
     方法论/字段收紧）混在一起呈现，部分提案的具体设计（如把方法论
     规则直接并入 16 条触发规则、STATUS 新增背景区节点）会重新制造
     "STATUS 体量失控"这个问题本身，或破坏 16 条规则"没有判断空间"
     这个核心性质

3. **按 blackbox 自身传统，走多方 AI 咨询（Claude/GPT/Gemini/DeepSeek/
   Qwen/MiniMax/Grok/Kimi 共 8 家）审核初稿，综合分歧后整合定稿，
   再更新 blackbox 本体（已选定）**
   - 优点：与 16 条规则/写入时机规则当年两轮多方咨询定稿的先例一致，
     不是单方面临时决定；8 家咨询意见高度收敛在"控制过度设计、能折叠
     进现有结构的不新增"这个共同判断上，帮助过滤掉初稿里会重蹈"规则
     写在纸上没人理"覆辙的部分设计
   - 缺点：流程更长，需要用户逐条拍板确认

## 决定 Decision

采用方案 3。最终整合定稿（`docs/ai-review-drafts/` 存档全文）相对下游
项目初稿有实质性修改，具体落地到 SKILL.md 的改动如下：

1. **STATUS 新增会话收尾摘要区块**（紧邻软锁标记，同一生命周期配对：
   软锁="我正在做"，摘要="我做完走了"），固定四段格式，≤300~400字，
   服务高频断片重启场景
2. **新增可选独立文件 CHARTER.md**（项目背景，几乎不变，跟 STATUS 的
   动态进展分开维护，不放进 STATUS 本体重复制造体量问题）
3. **CHANGELOG 新增"证据类型"字段**（直接枚举/查询｜间接推断｜工具
   报告｜设计意图源头），替代下游初稿"三条独立方法论触发规则"这个
   会破坏 16 条纯粹性的设计——一个字段即可暴露三类反模式
4. **CHANGELOG 版本指纹/验证结果两字段收紧为硬卡点**（仅命中修复/
   决策/重建/撤回/不可逆类型时强制），核心原则"可以写未验证/未知，
   但不能把未知/推断包装成通过"
5. **毕业文件新增两类**：任务归属追踪表（触发：共享任务队列且≥2并发
   写入者，人也算一个写入者；状态机含"完成→复开"回头路；本表是任务
   ID 唯一签发方）、多 agent 协作协议（触发条件相同但独立文件；含
   读写权限矩阵/STATUS 单一写者模式/任务派发格式/【假设】【待确认】
   【已确认】三态标注）
6. **新增"框架自检"一节**：归档硬触发（体量/时间跨度阈值机器可判断，
   不再是"应该"）、漏记检测（比对操作日志与 CHANGELOG，量化执行率）
7. **新增"凭据处理"一节**（此前完全空白）：脱敏点定在"生成诊断文本
   的那一刻"，不是"落笔进受版本控制文件的那一刻"；补充泄露后的补救
   流程（轮换+记录+评估历史清理），此前只有预防没有补救

## 理由 Rationale

- 8 家咨询意见的最强共识：证据 9 本身已经证明"规则不够"不是当前瓶颈，
  "已有规则执行率不到 100%"才是——一次性加太多新结构会重演这个问题，
  所以最终定稿刻意做"能折叠进现有结构的不新增字段/文件"的收敛，原
  7 条精简为 6 条落地项（原提案④整条并入⑥的证据类型字段），只新增
  2 类真正意义上的新机制（框架自检、凭据处理），而非全盘照搬初稿
- 任务归属追踪表和多 agent 协作协议的触发条件精确定义为"共享任务
  队列+≥2并发写入者"而非"agent数量"，是吸收咨询意见后的修正——避免
  单 agent+用户并行这类真实场景被阈值定义漏掉
- STATUS 会话收尾摘要区块与 CHARTER 分开设计（前者动态高频、后者
  静态几乎不变），呼应本条 ADR 修复的核心问题本身（不同变更频率的
  内容混在同一文件是体量失控的根因），设计上自洽

## 不确定性 Uncertainties

- 归档硬触发的具体阈值数值（体量50~100KB/时间跨度7~14天）是本轮咨询
  给出的建议区间，未在多个真实项目验证过是否普适，具体数值留给各
  下游项目按自身复杂度调整，本 ADR 不锁定唯一数字
- 任务归属追踪表 vs 协作协议是否应该合并为一份文件，8 家咨询意见中
  6 家反对合并（触发条件相同但变更频率不同），1 家（minimax）主张
  合并，本决定采纳多数意见但不代表分歧完全消失，留待后续实践验证
- 证据类型字段能否真正被 agent 老实填写（而非机械地全部填"直接枚举/
  查询"敷衍了事），依赖执行纪律，暂无技术强制手段——与本 SKILL.md
  其他软约束（比如 STATUS 软锁）是同一类局限

## 撤销/回退方案 Rollback Plan

如果实践证明某一条新增机制的维护成本明显高于收益（比如证据类型字段
被普遍敷衍、任务归属追踪表和 STATUS 待办清单出现内容重复打架），可以
单独收紧或废弃对应一条，不需要推翻整份补丁——每条改动在 SKILL.md 里
位置相对独立，撤回单条的影响面可控。建议先在下游项目 hermes-nas-
experiment 试点观察真实摩擦成本（优先关注任务归属追踪表和框架自检
两条，对应今天最贵的两次教训），再决定要不要在更多项目全量推广。

## 接受的风险/未处理的问题 Accepted Risks

- 本次补丁没有解决"多 agent 场景下如何做原子性并发写入 CHANGELOG/
  任务归属追踪表"这个更底层的技术问题——协作协议里的"单一写者模式"
  只解决 STATUS 这一个高风险文件，CHANGELOG/任务追踪表仍然依赖
  append-only 追加这个较弱的并发保证，理论上仍存在极小概率的写入
  时序交错问题，本次未处理
- 本轮咨询意见里提到的"版本指纹算法未统一"（deepseek提出，建议统一
  用 sha256 短码或 path+mtime+size 约定）本次没有正式采纳进 SKILL.md，
  留作后续可能的补充议题，不影响本次核心决定

## 影响 Consequences

- 好处：blackbox 从"单 agent 跨时间接续"场景扩展到覆盖"多具名 agent
  并行协作"场景，且是基于真实事故证据+多方 AI 审核后的收敛结果，不是
  凭空设计；框架自检机制（归档硬触发+漏记检测）第一次让"规则执行率"
  变成可量化指标，而不是只能靠印象判断
- 代价：SKILL.md 正文长度增加，新用户首次通读的认知负担相应上升；
  多出 3 份新模板文件（CHARTER/任务归属追踪表/协作协议）需要维护
