# ADR-0003：把 blackbox 本体纳入 git 版本控制

- **状态**：accepted
- **日期**：2026-07-24
- **补记**：否

## 背景 Context

排查 override-rules-fork-ops 那次真实违规（hermes 未经确认修改共享 Skill
定义）时，hermes 反过来去核实"blackbox 是不是也被改过"，发现自己没有任何
可靠的依据——只能靠文件的 mtime 做间接推理，无法真正确认"现在磁盘上这份
和官方版本是否一致"。

根本原因是：blackbox 从创建到历次修复，一直只是在对话里生成、打包成
`.skill` 文件发给用户下载，**没有一个独立于"某次对话"的、持久的、可核对
的存放位置**。`blackbox-project-record` 这个仓库虽然记录了"blackbox 经历
过什么"（CHANGELOG、ADR），但没有把 blackbox 的源文件本身放进去——记录的
是"关于它的历史"，不是"它本身的可核对版本"。

## 考虑过的选项 Options Considered

1. **维持现状**：继续靠对话生成 + 打包 `.skill` 文件发送
   - 优点：不需要额外搭建仓库
   - 缺点：没有任何独立第三方可以核实"这份是不是官方版本"，每次都要
     依赖"user/Claude 说一致就是一致"，这次的问题已经证明这个信任链不够
2. **只把 blackbox 的历史记录（STATUS/CHANGELOG/ADR）放进 git，源文件
   （SKILL.md/assets/）继续靠对话分发**（也就是现状，`blackbox-project-record`
   已经是这样）
   - 优点：改动最小
   - 缺点：记录了"发生过什么"，但没解决"现在这份是不是对的"这个核心
     问题——这正是这次事故暴露出来的缺口
3. **把 SKILL.md、assets/ 源文件本身，连同项目自己的记录，一起纳入 git
   仓库（已选定）**
   - 优点：任何时候都能 `git clone`/`git pull` 拿到确定无疑的版本，
     `git diff`/`git log` 直接给出"有没有被改过、改了什么"的确切答案，
     不再需要靠 mtime 或"信任对话记录"这种间接方式
   - 缺点：多一个仓库要维护，多一步"记得同步"的操作（改了 skill 之后
     要记得推送更新，不能只在对话里改完就算完）

## 决定 Decision

采用方案 3。新建一个独立的 git 仓库存放 blackbox 的完整内容（源文件 +
自身的记录），设为公开仓库（内容不含任何敏感信息，公开更方便任何工具/
agent 直接读取，不需要处理权限）。

## 理由 Rationale

- 这次事故的根源就是"没有独立可信的版本源"，解决方案必须直接对症
- blackbox 内容本身不敏感，公开仓库的维护成本最低，且方便 hermes 等
  agent 未来直接拉取，不需要额外配置访问权限

## 不确定性 Uncertainties

- 仓库建好后，谁负责在 blackbox 有更新时同步推送——目前的流程是"在对话
  里改完，用户手动同步到仓库"，还没有自动化，如果哪次忘了同步，仓库里
  的版本会滞后于对话里实际交付的版本，需要靠使用纪律保证，暂无技术强制

## 撤销/回退方案 Rollback Plan

如果这个仓库因为维护负担被放弃更新，直接停用即可——不影响 blackbox 本身
的使用（继续靠对话交付退回到方案 1），只是重新丢失"独立可核验版本"这个
能力，等同于回到这次事故暴露问题之前的状态。

## 接受的风险/未处理的问题 Accepted Risks

- 没有自动化机制强制"改完 skill 必须同步推送仓库"，依赖使用者自觉，
  这条本身也是一种"软约束"，跟 STATUS 软锁是同一类局限

## 影响 Consequences

- 好处：以后任何人（包括 hermes）想确认"这份 blackbox 是不是官方最新版"，
  直接对照这个仓库即可，不再需要靠间接推理或者单纯信任对话记录
- 代价：多了一个需要记得维护同步的仓库
