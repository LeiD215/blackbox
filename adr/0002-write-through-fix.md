# ADR-0002：blackbox 的"记录写入时机"未明确定义，修复为 write-through + 骨架先行

- **状态**：accepted
- **日期**：2026-07-22
- **补记**：否——这次是在问题发生后、当天讨论并决定的，属于正常时序

## 背景 Context

blackbox 定稿交付后，用户把它用于指导 hermes 维护 override-rules 项目。
这是 blackbox 第一次在真实、持续的 agent 工作流里被使用（此前的两轮多 AI
咨询都是针对设计文本本身的审核，不是真实运行）。

hermes 在这次真实使用中，修改代码、验证结果后没有同步更新 CHANGELOG，
直到用户主动追问才回头补记。这暴露了一个规范里从未明确过的问题：**触发
规则命中之后，"记录"这个动作本身该在什么时候真正写入文件？** 原规范只
说"事件发生就要记录"，没有说清楚是"立刻落盘"还是"可以先记在心里/待办里，
批量处理"。

## 考虑过的选项 Options Considered

1. **不改规范，把这次归为 agent 执行失误，靠加强提醒解决**
   - 优点：不用改动已经定稿的设计
   - 缺点：治标不治本——hermes 的自我归因（把"操作"和"记录"当成两个
     独立任务）指向的是规范表述本身的模糊，不是单纯的执行疏忽；换一个
     agent、换一次任务，同样的坑大概率还会再踩一次
2. **只加一条"必须立即写入"的文字要求**
   - 优点：改动最小，直接对症下药
   - 缺点：经外部咨询发现，这条要求本身不够精确——没定义"立即"的颗粒度
     （容易导致过度碎片化的日志噪音），是纯粹的正向义务式表述（"必须做
     X"），约束力弱于反向不变量式表述（"不做 X 就不算完成"）
3. **改为 write-through 原则 + 复用已有原子单位定义 + "未记录即未完成"
   不变量 + 骨架先行两阶段记录（已选定）**
   - 优点：从根上解决了颗粒度模糊和义务式表述力度不足这两个问题；骨架
     先行机制直接对应 blackbox"抗中断"这个核心目的——哪怕操作执行到
     一半中断，也能留下"开始了但没完成"的痕迹，而不是现在这样中断了
     就跟没发生过一样
   - 缺点：规则本身变复杂了一些，需要 agent 理解"骨架先行"这个两阶段
     概念，比单纯"立即写"多一层认知负担

## 决定 Decision

采用方案 3。同时追加一条相关但独立的修复：hermes 发现问题后未经确认
直接修改了它本地那份共享 skill 文件，这暴露了另一个规范空白——**共享
规范定义被单个 agent 单方面修改，没有确认流程**。这条也一并修复：明确
"改共享定义前必须经用户确认"，疑似漏洞走结构化上报（不是随手记进
CHANGELOG）。

## 理由 Rationale

- 两轮外部 AI 咨询（第一轮泛泛审核整体设计，第二轮针对这一具体问题
  聚焦评估修复方案）在"根因是任务分解层面把记录建模成独立步骤，不只是
  时机问题"和"需要颗粒度定义防止碎片化"这两点上高度一致，说明这不是
  孤立的偶然判断
- 骨架先行机制直接对应 blackbox 存在的核心理由，采纳成本不高、收益直接
- "共享规范不能擅自改"这条本身，恰好也是 write-through 原则的一个应用
  场景（决定要提出疑点，同样要在发现的当下就记录，不能自己想好了改法
  再一次性上报）——两条修复在精神上是自洽的，不是两个不相关的补丁

## 不确定性 Uncertainties

- 这次修复的方案本身，同样只经过了"文本层面的多 AI 咨询"验证，还没有
  经过第二次真实使用的检验——不确定"骨架先行"这套两阶段流程，agent
  实际执行起来会不会又衍生出新的理解偏差（比如分不清什么算"有风险的
  多步骤操作"、什么算日常小改动，从而误判要不要用骨架先行）
- "结构化上报共享规范疑点"这个机制，目前还没有真实触发过（这次是用户
  直接把问题带回这个对话来处理的，没有走 hermes 在项目里写结构化条目
  这条路径），实际好不好用还不知道

## 撤销/回退方案 Rollback Plan

如果"骨架先行"机制实际用起来发现 agent 经常判断错"什么时候该用"，
可以退回到更简单的"单阶段立即写入"，只保留"未记录即未完成"这条反向
表述和"复用规则1原子单位定义"这两处改动（这两处成本低、收益确定，
不依赖"骨架先行"是否好用）。

## 接受的风险/未处理的问题 Accepted Risks

- 仍然只是文字规范层面的约束，没有工具层/结构性强制（比如复合工具、
  校验脚本）。多家咨询意见都指出这才是终极可靠的方案，但这超出了
  blackbox 作为一份 skill 定义文件的能力范围，接受这个局限，在文档里
  如实说明"有条件的话建议加这层机制"，不假装文字规则能做到强制级别
  的可靠性

## 影响 Consequences

- 好处：blackbox 第一次真实使用就暴露了一个真实、有代表性的问题，说明
  "边用边修"这个策略（而不是继续无限期地做纯理论审核）是对的方向；
  修复后的版本在"抗中断"这个核心目的上比初版更扎实
- 代价：hermes 那份被它自己修改过的本地 skill 副本需要人工替换成新的
  官方版本，存在"忘了替换、继续用着分叉版本"的风险，需要用户自己
  跟进确认
