# 多 Agent 协作协议

## 角色 + 职责边界

| 代号 | 职责范围 | 不做的事 |
|---|---|---|
| （示例）哨兵 | 基础设施/infra问题修复 | 不碰主线项目实质性代码 |
| （示例）驻站 | 主线项目实质性工作 | 不碰基础设施细节 |

## 读写权限矩阵（系统事实，不是流程建议）

| 文件/资源 | 谁能写 | 谁能标记完成 | 冲突时谁裁决 |
|---|---|---|---|
| STATUS.md | 仅单一写者（见下） | — | 单一写者 |
| CHANGELOG.md | 任何角色（append-only，低风险） | — | — |
| 任务归属追踪表 | Owner本人更新自己名下条目 | Owner本人+复核方 | 单一写者/用户 |
| 生产环境部署 | 按红线规则单独定义 | — | 用户 |

**STATUS 单一写者模式**：由一个持续在场、承担协调职责的角色实际改写
STATUS，其他 agent 通过 CHANGELOG/任务归属追踪表提交变更内容，由单一
写者定期整合进 STATUS。不建议"STATUS 由 CHANGELOG 自动派生生成"——
引入自动生成工具链会牺牲"任何人打开就能读懂""任何环境都能用"这两条
blackbox 一贯的设计前提。

## 任务派发格式规范

派发一条任务至少包含：

```
任务ID: TT-<项目名>-<编号>（引用任务归属追踪表，不自造编号）
目标: 一句话
验收标准: xxx
依赖: xxx（如果有）
Owner: xxx
TTL: 预计多久（可选但建议填）
汇报点: 完成/阻塞时向谁汇报
```

## 轻量级判断标注三态

不复用 ADR 的 `proposed/accepted`（那描述的是决策文档生命周期，跟
日常轻量判断不是同一层东西）。

- **【假设】**——agent 自行推断、填补的空白，用户未见过，**必须标，
  不标即违规**
- **【待确认】**——已呈报，等用户
- **【已确认】**——用户拍板

**关键约束**：一旦【假设】状态的内容被任何下游动作引用，必须先升格
为【待确认】，不能让"假设"默默变成"既定事实"被后续工作继续沿用。

## 冲突处理

- 两个 agent 同时想动同一份文件/同一个任务：先认领的优先，后来者
  等待或找单一写者/用户裁决，不允许都动手
- 任务 TTL 到期没人认领/更新：视为释放，其他 agent 可以接手，但要
  在任务归属追踪表的状态历史里留一笔"接管了过期任务"
